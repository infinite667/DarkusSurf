# DarkusSurf v0.4.0 — Windows network tools preview
**Privacy. Control. Anonymity.**

> Historical v0.4.0 user guide. The GitHub source checkout omits the downloaded Tor binaries; follow [vendor setup](../vendor/tor/README.md) before building. The original preview is not cleared for public binary redistribution.

DarkusSurf is an independent, no-telemetry Tor controller with opt-in browser proxy profiles for Windows and Linux. It is not a VPN, operating-system firewall or audited anonymity tool. It is not affiliated with the Tor Project.

## Quick start (Windows x64)
1. Extract the standalone ZIP. Review the included notices and verify the supplied Tor Expert Bundle against the official signed release. Its original signature was not supplied or independently verified. The executable is unsigned.
2. Double-click `DarkusSurf.exe`. Python, Go and separate Tor installation are not required. The Windows executable opens a dedicated Win32/GDI desktop window with no local dashboard web server, external browser, WebView, CGo or visible console. The native OS title bar is used; dark title bar is requested on supported Windows versions. The dark-purple interface is custom drawn and supports mouse and Tab/Shift+Tab, Enter and Space; it has not been screen-reader audited.
3. Click **Connect to Tor** and wait for bootstrap. Optionally click **Verify Tor exit** to check one HTTPS request made by the backend through Tor.
4. Open **Applications**. Select one or more browsers (Firefox, Chrome, Edge, Chromium, Brave), click **Save selection**, then **Launch via Tor** next to a selected browser. A new independent browser profile is created with a local SOCKS5 proxy. This browser-launch action does not modify existing browser or Windows network settings. The separate Windows proxy mode is opt-in.
5. The new window opens https://check.torproject.org/ automatically. Confirm the Tor Project page reports a Tor connection and check the IP in that new window. Compare with an existing ordinary browser window, which should continue using your direct connection (or existing VPN/proxy). Do not assume that the launch or internal verification proves the browser connection.
6. To stop, close the launched browser windows, then click Disconnect or Exit. Ordinary windows remain unaffected unless the optional Windows proxy was enabled; disconnect restores the previous proxy settings. Reconnecting requires a new launch. On Windows the controller can remain running in the tray after minimizing or closing (if enabled and tray registration succeeds); use Exit DarkusSurf to stop it. Linux retains the older browser dashboard and five-minute UI-polling idle timeout.

Browser detection checks standard locations and registered Windows App Paths (except Chromium, which shares Chrome’s executable name), or PATH on Linux. You can select undetected browsers but cannot launch them until detected. Selection is available before Tor connects. The application page shows why a launch is unavailable. Other apps can be configured manually with the dashboard SOCKS5 address if they support it. Remote DNS (SOCKS5h) should be enabled for those apps. Arbitrary EXE selection is not implemented. Linux sandboxed browser packages may not accept the temporary profile path.

## Windows native features
- Dashboard, Applications, Network, Traffic, Circuits, Bridges, Diagnostics, Settings and About pages in a dedicated desktop window. No third-party Go modules. The dashboard uses Win32/GDI rather than the earlier proposed Gio framework.
- Single instance per interactive Windows session. Starting the EXE again attempts to restore the existing window. If the tray icon is available, minimize/close to tray is optional. Left or right click the tray icon to restore; choose Exit DarkusSurf to shut down.
- Settings and application selections use the existing JSON file and migrate old selections. The compact option makes the window smaller on next launch; automatic verification, automatic reconnection and tray behavior apply after saving.
- Automatic reconnection is disabled by default, can be enabled under Settings, and tries at most three times per failure sequence (5, 10, 20 second delays). A manual disconnect cancels retries. A successful connection resets the retry count. Reconnection does not reattach or restart old browser profiles; close them and launch new ones. This is not a kill switch.
- No firewall changes; the optional Windows proxy mode changes current-user default LAN proxy settings only after explicit confirmation. Launch via Tor still opens an installed supported browser in its own profile. A successful controller verification is not proof that ordinary windows use Tor.
- Native window rendering, tray interaction, clipboard, native shutdown and real Tor/browser connection still require a Windows test. See [WINDOWS-TEST-CHECKLIST.md](../WINDOWS-TEST-CHECKLIST.md).

## Scope and limitations
- Each launched browser gets a temporary profile and an individual loopback TCP relay tied to one Tor session. The relay forwards only to that session's Tor SOCKS listener and refuses new connections after disconnect or session replacement. It remains bound until the controller exits. This is **not** an OS-level kill switch: browser components can make connections outside their proxy settings, and no firewall prevents them. Do not leave these browser windows open after controller exit. Browser profile preferences and command-line flags are not security enforcement.
- Firefox profiles request SOCKS5 remote DNS and disable direct proxy fallback, DNS prefetch, WebRTC, and HTTP/3. Chromium-family profiles specify a SOCKS5 proxy and request restrictions on DNS resolution, QUIC and non-proxied WebRTC UDP. Actual browser behavior varies by version, policies and background components. Tor is now configured with SafeSocks and NoIPv6Traffic for its SOCKS listener; Firefox profiles also disable IPv6 DNS lookups. These measures only cover the managed proxy/profile, and DNS/IPv6/WebRTC leaks have not been independently tested. Tor does not transport arbitrary UDP. No promise of anonymity is made.
- The Tor Project recommends using official Tor Browser rather than other browsers for anonymity-sensitive browsing: https://support.torproject.org/tor-browser/security/using-tor-with-other-browsers/ . Do not use this preview for sensitive activity.
- Ordinary apps are not automatically routed by default. The optional Windows system proxy applies only to proxy-aware HTTP/HTTPS clients. Exclusion mode, arbitrary app interception, OS firewall enforcement, true system-wide routing, OS-wide DNS/IPv6 leak protection and signed updates remain unimplemented. The Traffic and Circuits pages report Tor counters and built circuits; bridge import supports vanilla and obfs4 in the Windows GUI. Windows now has a native GUI, system tray, single-instance check, and optional bounded reconnection; Linux retains its local web GUI.
- Temporary profile and Tor data files are removed on normal exit where possible, not securely erased; browser locks or crashes can leave files behind. Close browser windows first. Settings persist in the current user's configuration directory (Windows `%APPDATA%\DarkusSurf\preferences.json`, Linux `$XDG_CONFIG_HOME/DarkusSurf/preferences.json` or `~/.config/DarkusSurf/preferences.json`). No browsing URLs or traffic destinations are recorded by DarkusSurf.

## Build from source
Go 1.23 or newer required; use a supported security-maintained release from https://go.dev/dl/. No third-party Go modules are required.
- Windows: run `Build-Windows.cmd` to produce `dist\DarkusSurf.exe`. `Launch-Windows.cmd` builds if needed and launches. The uploaded Windows Tor bundle is embedded, along with its notices and the supplied logo. No C compiler is needed for regular builds.
- Linux: install Go, trusted Tor and xdg-utils (Debian/Ubuntu: `sudo apt install tor xdg-utils`), then `chmod +x Build-Linux.sh Launch-Linux.sh scripts/Build-Linux.sh` and `./Build-Linux.sh`. Output: `dist/DarkusSurf`. Linux can use a verified expert bundle at `dist/vendor/tor/linux/` next to the binary, with `tor/tor` executable, or the system Tor package. The Linux bundle was not supplied and is not embedded.
- Both platforms share the controller and routing backend, including traffic sampling and SOCKS settings; the new controls are exposed only in the Windows native GUI. Linux keeps its previous interface. Browser detection and UI differ by OS. Tor startup uses a temporary isolated data directory, local random ports and cookie-authenticated control protocol. Only the Linux web UI uses a local-only HTTP listener, random bearer token, Host and Origin validation and no external UI resources.

## v0.4.0 Windows feature guide

- **Network:** Windows system proxy is OFF by default. Connect Tor, open Network, and confirm Enable Windows proxy. It sets the current user's default WinINet LAN HTTP/HTTPS proxy to an ephemeral local HTTP relay which sends supported requests through the current Tor SOCKS session. It does not change WinHTTP, VPN interfaces, firewall, DNS servers, or routes. Apps may ignore system proxy, bypass it for local hosts or use UDP. Restart applications if they cache proxy settings. Verify each actual application; no system-wide anonymity is promised.
- **Restoration:** Before applying settings, DarkusSurf writes a local recovery journal under `%APPDATA%\DarkusSurf\system-proxy-restore.json` containing previous proxy settings. Restore original Windows proxy, Disconnect, and Exit attempt restoration. A crash may leave Windows pointing to a dead local proxy; relaunch DarkusSurf to recover. If settings have changed externally, it refuses to overwrite them and reports a warning. If automatic recovery fails, use Windows Settings > Network & internet > Proxy and restore your prior configuration manually; keep the journal for reference. Restoring the proxy permits normal direct network access where applicable. No firewall kill switch is provided.
- **Traffic:** Live Tor-process byte totals and sampled download/upload rates, not device-wide bandwidth or per-application counters. The control protocol reports cumulative traffic including Tor overhead.
- **Circuits:** Shows up to four built general-purpose circuits, using relay nicknames or shortened fingerprints. They are not tied to the currently viewed site. Circuit refresh is off on every launch and stops when Tor disconnects. Select a requested interval from 3 to 30 seconds, in 3-second steps. Actual requests are at least 10 seconds apart and subject to further Tor rate limits. New circuits are for future requests; existing connections are not migrated and a new IP is not guaranteed. Controller IP verification is invalidated after a renewal request. No untraceability claim.
- **Bridges:** Copy trusted vanilla or obfs4 bridge lines from https://bridges.torproject.org/ and import via clipboard while disconnected. Clear to return to normal Tor. Bridges are kept in memory for the app session, not saved to preferences. The transport binary is included in the uploaded bundle. Actual bridge bootstrapping on Windows is untested.
- **Privacy:** Managed browser preferences request remote DNS and limit direct UDP/WebRTC/QUIC behavior. Tor SafeSocks rejects unsafe IP-only requests, and NoIPv6Traffic restricts IPv6 destinations through the SOCKS listener. The HTTP relay does not perform direct DNS resolution and blocks IPv6 literal and local destinations. These controls cannot prevent all OS or browser background leaks. Independent DNS/IPv6/WebRTC leak tests and an OS-level firewall are still required.
